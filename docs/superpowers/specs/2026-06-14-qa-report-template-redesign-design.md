# QA 보고서 템플릿 재설계 (Report Template Redesign)

## 목적

현재 `ReportRenderEngine.java`의 `renderMarkdown()` 메서드가 생성하는 보고서는 다음 문제를 가지고 있다:

1. **RAG Evidence 덤프**: 각 TC의 근거 문서 조각이 SRS/SDD 원문 수백 줄을 raw 텍스트로 반복 출력
2. **위험 요소 태그 과잉**: TC당 20~30개의 중복·무관 해시태그 나열
3. **QA 용어 미설명**: 사전 조건, 기대 결과, 신뢰도 등 QA 전문 용어 설명 없음
4. **들여쓰기 불일치**: 일부 필드는 불릿, 일부는 독립 헤더 혼용

이 문서는 위 문제를 해결하기 위한 템플릿 전면 재설계 사양을 정의한다.

## 섹션별 명세

### Section 0. 이 보고서를 읽는 방법 (신규)

보고서 최상단에 고정 삽입되는 용어 안내 블록이다.

```markdown
## 0. 이 보고서를 읽는 방법

이 보고서는 AI가 프로젝트 요구사항 문서를 분석하여 자동 생성한 QA 검증 보고서입니다.
테스트 및 QA 경험이 없어도 아래 용어 설명을 참고하면 내용을 이해할 수 있습니다.

| 용어 | 설명 |
|------|------|
| 테스트 케이스 (TC) | 특정 기능이 올바르게 동작하는지 확인하기 위한 하나의 검증 시나리오 |
| 우선순위 | HIGH: 반드시 검증 / MEDIUM: 가능하면 검증 / LOW: 여유 시 검증 |
| 신뢰도 | AI가 이 테스트 케이스를 얼마나 확신하는지의 정도 (HIGH/MEDIUM/LOW) |
| 사전 조건 | 테스트를 시작하기 전에 반드시 갖춰야 할 환경이나 상태 |
| 테스트 절차 | 테스트를 수행하는 순서대로 나열한 단계별 행동 목록 |
| 기대 결과 | 테스트가 통과할 때 나타나야 하는 정상적인 결과 |
| 위험 요인 | 이 기능에서 발생할 수 있는 잠재적인 문제나 취약점 |
| 근거 출처 | AI가 이 테스트 케이스를 생성할 때 참고한 문서 |
| 보완 시나리오 | RAG 분석 외에 LLM이 추가로 제안한 테스트 시나리오 |
```

### Section 3. 테스트 케이스 목록

#### 3-1. TC 형식 (들여쓰기 규칙 포함)

모든 최상위 필드는 `- **필드명**:` 형식을 사용한다.
하위 항목은 2칸 들여쓰기를 적용한다:
- 절차(순서 있음): `  1.`, `  2.`, ...
- 목록(순서 없음): `  - `

```markdown
### TC-001: 관리자가 사용자 문의 확인 및 답변하기

- **우선순위**: `HIGH` | **신뢰도**: `HIGH`
- **검증 대상**: REQ-015 — 관리자는 사용자가 등록한 문의를 확인하고 답변할 수 있어야 한다.
- **테스트 시나리오**: 관리자가 문의를 확인하고 적절한 답변을 입력하여 저장하는 시나리오
- **사전 조건**: 관리자 계정으로 로그인되어 있어야 하며, 사용자가 등록한 문의가 존재해야 한다.
- **테스트 절차**:
  1. 관리자 대시보드로 이동한다.
  2. '문의 관리' 섹션을 클릭한다.
  3. 특정 사용자의 문의를 선택한다.
  4. 답변 입력란에 적절한 답변을 입력한다.
  5. '답변 저장' 버튼을 클릭한다.
- **기대 결과**: 문의에 대한 답변이 성공적으로 저장되고, 사용자에게 알림이 전송된다.
- **위험 요인**:
  - 접근 권한이 없는 사용자의 요청이 차단되는지 검증이 필요합니다.
  - 예외 상황 발생 시 적절한 오류 응답이 반환되어야 합니다.
- **근거 출처**:
  - DOC-18BD6CAB_SRS.md (소프트웨어 요구사항 명세서)
  - owasp_security_knowledge_cards.json (보안 검증 가이드)
```

#### 3-2. 위험 요인 태그 → 문장 변환 규칙

`ReportRenderEngine.java`에 다음 매핑 테이블을 구현한다.
태그 목록을 순회하며 그룹에 해당하는 문장을 추가한다. 중복 문장은 제거한다.
매핑되지 않는 태그는 출력하지 않는다. 매칭되는 문장이 하나도 없으면 위험 요인 섹션 자체를 생략한다.

| 태그 키워드 (포함 시 매칭) | 출력 문장 |
|--------------------------|-----------|
| 권한_부여, 권한검증, 관리자, AUTHORIZATION_BYPASS, PRIVILEGE_ESCALATION | 접근 권한이 없는 사용자의 요청이 차단되는지 검증이 필요합니다. |
| 입력검증, 유효성검사, 입력오류, 데이터유효성 | 잘못된 입력값에 대해 서버가 적절히 거부하는지 확인이 필요합니다. |
| 오류처리, 예외처리, 서버오류, 오류 | 예외 상황 발생 시 적절한 오류 응답이 반환되어야 합니다. |
| 로그인, 전화번호, 인증 | 인증 정보의 정확성과 보안 처리 여부를 확인해야 합니다. |
| 출석, 위치검증, GPS, 위치오류 | 위치 데이터의 정확성과 출석 처리 로직의 신뢰성을 검증해야 합니다. |
| 엑셀업로드, 파일다운로드 | 파일 입출력 처리 중 데이터 손실이나 오류가 없는지 확인이 필요합니다. |
| TEST_COUPLING, TEST_STATE_POLLUTION | 테스트 간 상태 공유로 인한 결과 오염 가능성이 있습니다. |
| CREDENTIAL_EXPOSURE | 민감 정보(비밀번호, 토큰)가 코드나 로그에 노출될 위험이 있습니다. |

#### 3-3. Evidence 렌더링 규칙

`ev.getEvidenceText()` 원문은 출력하지 않는다.
`ev.getSourceName()`만 출력하되 동일한 소스명은 중복 제거한다.

소스명에서 파일 유형별 읽기 쉬운 레이블로 변환한다:

| 소스명 패턴 | 표시 레이블 |
|------------|------------|
| `*_SRS.md` | 소프트웨어 요구사항 명세서 |
| `*_SDD.md` | 소프트웨어 설계 문서 |
| `owasp_*` | 보안 검증 가이드 (OWASP) |
| `istqb_*` | 테스트 기법 가이드 (ISTQB) |
| `cypress_*` | E2E 테스트 모범 사례 (Cypress) |
| `playwright_*` | E2E 테스트 기법 (Playwright) |
| `nist_*` | 테스트 프로세스 가이드 (NIST/SAMATE) |
| 기타 | 소스명 그대로 표시 |

## 구현 범위

`ReportRenderEngine.java`의 `renderMarkdown()` 메서드만 수정한다.
백엔드 도메인 모델(Evidence, RiskItem, AnalysisJob 등)은 변경하지 않는다.

추가 구현 항목:
- `buildRiskSentences(List<?> risks)` private 메서드 — 태그 → 문장 변환
- `formatSourceLabel(String sourceName)` private 메서드 — 소스명 → 레이블 변환
- `deduplicateSources(List<?> evidences)` private 메서드 — 중복 소스 제거
